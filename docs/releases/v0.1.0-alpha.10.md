# Intern v0.1.0-alpha.10

This is an alpha release for Windows x86-64. It is deliberately published as a
GitHub **latest** release—not a GitHub prerelease—so installed clients can
continue to fetch the updater manifest at
`/releases/latest/download/latest.json`. The version and this note still make
its alpha status explicit.

## Since alpha.9

### Read this first if you watch a shared folder

**This build cannot verify who uploaded a document to a shared folder.** In
alpha.9 you connected Microsoft upload verification by typing a tenant ID and an
application ID, and Intern checked SharePoint audit records. That connection is
gone.

It is being replaced by a fixed connection to one SharePoint library that asks
you for nothing. That connection only works in a build provisioned with the
library's Microsoft identifiers, and this build is not.

What that means on this build:

- **Documents in a OneDrive, SharePoint, or network-share intake folder stay
  held.** Intern does not process them. It never guesses who put them there,
  and it never reads a file it cannot attribute to you.
- **A folder on this computer that is not shared still works** as a private
  local intake, exactly as before.
- **Dragging documents onto the window, naming, review, and filing are
  unchanged.**

If you relied on the verified shared intake, you can stay on alpha.9 until a
build provisioned for your SharePoint library is published.

### Guided SharePoint setup (built, switched off in this build)

This release contains the new setup for the fixed SharePoint library. It does
nothing until a build is provisioned. Once it is, Intern walks a new or updated
installation through each step:

1. Getting the local model.
2. Signing in with a Microsoft work account and confirming it is the account
   documents are uploaded with.
3. Asking OneDrive to sync the library.
4. Recognising the synced folder from OneDrive's own records rather than from its
   name.
5. Turning on filing from `Files/Inbox` into `Files/Filed`.

After setup, Settings shows a read-only connection summary instead of folder
pickers and identifiers.

Only documents uploaded by the connected account after setup are processed. The
design and its limits are described in the
[administrator guide](../sharepoint-deployment.md), including that a same-account
copy or move into the Inbox cannot be told apart from a direct upload.

### The model download no longer gives up on one dropped connection

The 1.19 GiB model download used to fail setup on the first dropped connection,
and you had to notice and press **Try download again**. It now resumes the same
download a few times, with a pause between attempts, before it reports a failure.

### Updates are checked for you

Intern used to look for updates only when you pressed **Check for updates** in
Settings, so a machine could sit on an old build indefinitely. It now also checks
once when it starts, and again at intervals while it keeps running. A new version
shows as a banner in the main window. Installing still always takes an explicit
click, and only a build signed by this project's key is accepted.

## Download, model, and update details

Supported target: **Windows 10 or 11, x86-64**, using the per-user NSIS
installer `Intern_0.1.0-alpha.10_x64-setup.exe`. It does not require
administrator rights. The installer contains the local parser/runtime but not
the 1.19 GiB local text model. On first run, Intern downloads that pinned model
only after you ask it to, or lets you choose an existing verified copy.

With the local model (the default), document text, OCR output, and prompts stay
on the machine. A hosted model, if you turn one on, receives the distilled text
of each document. This build makes no Microsoft connection at all.

Use **Check for updates** in Settings to fetch GitHub's latest manifest; Intern
also checks automatically, as described above. The client installs only an
updater payload whose detached Minisign signature verifies against the public
key compiled into the application. Before creating release evidence, the release
workflow independently verifies:

- the exact installer;
- its detached signature;
- the URL, version, and signature recorded in `latest.json`.

`SHA256SUMS.txt` covers every distributable release file exactly once. It leaves
out itself and `release-evidence-manifest.json`, to avoid a checksum cycle.

The evidence manifest hashes the checksum file. It also binds:

- the installer and updater manifest;
- the runtime inventory and notices;
- the SBOMs;
- the smoke, evaluation, and fidelity evidence;
- the logs.

Verify the installer provenance as well:

```sh
gh attestation verify Intern_0.1.0-alpha.10_x64-setup.exe --repo z-brenner/intern
```

The installer is **not Authenticode signed**: this project has no Windows
code-signing certificate. Windows/SmartScreen may warn about an unrecognized
app even when the updater signature and GitHub provenance check pass. Treat the
warning seriously, verify the checksum and provenance, then use **More info** →
**Run anyway** only if you trust the release.
